## Interesting Findings

### Engine Architecture And Core Loop

- `src/commonMain/kotlin/main.kt` uses `AsyncInjector` to wire stage, event bus, sprites, level, field, resolution, audio, renderer, scoring, animation, and input as separate collaborators instead of building everything inside one scene class.
- `src/commonMain/kotlin/j4k/candycrush/GameFlow.kt` models the match-3 loop as an event-driven pipeline triggered by `DragTileEvent`, then sequences swap, deletion, gravity, refill, and recursive cascade checks through animation-completion callbacks.
- `src/commonMain/kotlin/j4k/candycrush/Events.kt` and `src/commonMain/kotlin/j4k/candycrush/lib/EventBus.kt` define a compact typed-event layer over KorGE's `GlobalBus`, which keeps scoring, objectives, actions, and HUD updates decoupled from the board logic.

### Rendering And Graphics

- `src/commonMain/kotlin/j4k/candycrush/renderer/GameFieldRenderer.kt` maintains a separate `CandyImage` grid that mirrors the logical `GameField`, which makes visual bookkeeping explicit and avoids treating rendered nodes as the source of truth.
- `src/commonMain/kotlin/j4k/candycrush/renderer/animation/TileAnimator.kt` updates the renderer grid before launching tweens for swaps, drops, and inserts, so the animation system follows stable movement commands instead of ad hoc per-frame reconciliation.
- `src/commonMain/kotlin/j4k/candycrush/config/CandySets.kt` maps logical `Tile` values to sprite-sheet slots, which is a useful pattern for skin/theme swapping without touching gameplay code.

### Gameplay Systems

- `src/commonMain/kotlin/j4k/candycrush/GameMechanics.kt` keeps match detection, swap validation, hole-based gravity, and refill command generation in one mostly pure board-logic class with no renderer dependency.
- `src/commonMain/kotlin/j4k/candycrush/model/Level.kt` supports an optional reserve field that feeds scripted next tiles per column before falling back to randomness, which is useful for handcrafted levels, tutorials, and deterministic tests.
- `src/commonMain/kotlin/j4k/candycrush/LevelCheck.kt` and `src/commonMain/kotlin/j4k/candycrush/Scoring.kt` consume bus events to track move limits, tile objectives, and combo multipliers without embedding those rules into `GameMechanics`.

### Input And Controls

- `src/commonMain/kotlin/j4k/candycrush/input/DragListener.kt` turns low-level pointer motion into thresholded drag events, which is a compact pattern for touch-driven board interactions.
- `src/commonMain/kotlin/j4k/candycrush/input/MoveTileObserver.kt` projects drag endpoints through `PositionGrid` and only emits adjacent-cell moves, keeping tile-adjacency validation at the input boundary before gameplay logic runs.

### UI, HUD, And Menus

- `src/commonMain/kotlin/j4k/candycrush/renderer/ScoringRenderer.kt` combines a persistent total-score HUD with short-lived floating score popups anchored to board positions, which is a strong feedback pattern for puzzle games.
- `src/commonMain/kotlin/j4k/candycrush/renderer/LevelCheckRenderer.kt` renders remaining moves and tile objectives as HUD widgets driven from `LevelCheck`, not from renderer-local counters.

### Physics And Collision

- No significant physics or collision systems were relevant in this repository.

### Tooling, Android Integration, Or Other Notable Areas

- `build.gradle.kts` exposes `targetJvm()`, `targetJs()`, `targetDesktop()`, and `targetAndroidIndirect()`, which shows how a single `commonMain` game sample can be packaged for Android while still staying runnable on desktop and web for development.
- `src/commonMain/kotlin/j4k/candycrush/audio/SoundMachine.kt` and `src/commonMain/kotlin/j4k/candycrush/audio/JukeBox.kt` separate short sound effects from looping playlist music, which is a clean service split for small games.
- `src/commonTest/kotlin/GameMechanicsTest.kt`, `GameFieldTest.kt`, `LevelTest.kt`, `PositionGridTest.kt`, and `TileTest.kt` give unusually good coverage for a sample repo, including board parsing, match detection, gravity, insert ordering, reserve behavior, and coordinate mapping.

## Reusable Takeaways

- Keep puzzle-board logic in a renderer-independent class and emit command objects for swaps, drops, and inserts.
- Use a typed event bus to connect scoring, objectives, actions, and HUD without creating direct cross-dependencies.
- Consider reserve-based tile feeds when a match-3 style game needs deterministic tutorial or handcrafted level behavior.
- Treat `commonTest` coverage as part of the reference value for gameplay repos, not as optional polish.
