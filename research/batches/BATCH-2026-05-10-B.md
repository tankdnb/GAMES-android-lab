## Lessons From This Batch

- A Compose-native engine (`pandulapeter/kubriko`) fits the repository goal especially well because it stays close to modern Android UI integration while still offering explicit engine subsystems.
- Strong engine repositories can still end up as `reference-only` if their runtime assumptions are too far from the lab's Android target, as happened with `AlmasB/FXGL`.
- Even moderate-size third-party Kotlin repos can make Gradle discovery too expensive for quick batching, which reaffirms the static-first workflow.
- It remains useful to mix one direct Android game with several framework references in the same batch so the catalog grows in both architecture and product patterns.
